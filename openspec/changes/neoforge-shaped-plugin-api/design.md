### How the generator classifies a row

| Column | Rule |
|:--|:--|
| Event | A class whose superclass chain reaches `net.neoforged.bus.api.Event`. Names resolve through nested classes, imports and the same package. |
| Bus | `mod` when the class or a supertype implements `IModBusEvent`, else `game`. |
| Side | `client` for the client source set, a `.client.` package, `FMLClientSetupEvent`, or an event that only client code constructs (`src/client`, patches under `net/minecraft/client` and `com/mojang/blaze3d`). `server` for `event.server`, the permission events, `FMLDedicatedServerSetupEvent`, or a constructor or field of a server-only type (`ServerPlayer`, `ServerLevel`, `MinecraftServer` and similar). `both` otherwise. NeoForge 26.3 has no `@OnlyIn` on API classes. |
| Cancel | The class or a supertype implements `ICancellableEvent`. |
| Result | Setters in the class or its superclasses that take a `Result` enum, a `TriState` or an `InteractionResult`. |
| Abstract | The eventbus rejects listeners on abstract event classes. An abstract row is `planned` when a subclass is supported or planned, and lists its subclass statuses. |
| Status | `supported`: a Pumpkin event or API exists today. For events, the generator checks that the struct exists, that code outside the events folder constructs it, and names the files and the WIT v0.2 exposure. A mapped Pumpkin event that nothing fires becomes `planned`. A non-event API claim is checked by a string search in the named file. `planned`: server-side and mappable to the named Pumpkin concept. `client-only`: never runs on a dedicated server. `not supported`: server-side, no Pumpkin equivalent and not planned; the reason says why. |
| Method rows | One row per public method name; overloads are counted in the Kind column. |

The status of each row comes from hand-written mapping tables next to the generator. The generator stops when a class has no mapping, a reason is empty, or a claimed Pumpkin event or API is missing from this checkout.

## Goals / Non-Goals

**Goals:**

- One row for every public NeoForge API element a server-side port touches, with side and status.
- Counts per family, so the size of each gap is visible.
- A row status that a later run can recheck against the Pumpkin tree.

**Non-Goals:**

- Hook-by-hook mapping of `IBlockExtension`, `IItemExtension` and the other extension interfaces. Each has one row here; the phase 4 mapping table splits them.
- What the reference modpack uses. That is `modpack-usage.md` (#46).
- The shape of the phase 4 crate. The decisions below fix the target, not the API design.

## Decisions

### The target is a NeoForge-shaped Wasm plugin API

Decided on 2026-10-07 and recorded in the pinned "Orchestration status" issue (#29). Ported mods become IronPumpkin plugins that use the same event, registry, capability and metadata names and structure as NeoForge. Loading real Java mod jars is out of scope, because a mod jar needs the whole `net.minecraft` Java API surface and Pumpkin does not have it. Rejected alternative: an embedded JVM or a NeoForge sidecar. It stays as the optional Java feasibility spike, which runs only on the owner's request.

### The inventory is generated; the statuses are hand-written and checked

Class lists, buses, sides, cancel flags, results, method counts, channel ids, registry lists and `neoforge.mods.toml` keys come from the sources. Statuses and Pumpkin concepts are judgement. The generator keeps judgement in mapping tables and checks every `supported` claim against this checkout. Rejected alternative: a hand-written list. It drifts on the next NeoForge commit and cannot be rechecked.

### `supported` means a ported mod gets the behaviour today

A Pumpkin event that exists but fires only for a subset of NeoForge's cases is `planned`, with the gap in the reason (for example `ArrowLooseEvent`: Pumpkin fires `EntityShootBowEvent` only from mob goals). Smaller gaps that keep the event usable stay `supported` and are named in the reason (for example `CropGrowEvent.Pre` sets a result in NeoForge and cancels in Pumpkin). The phase 4 mapping table verifies each supported row with a test.

### Names follow NeoForge 26.3, not older guides

Some NeoForge 26.3 names differ from older porting guides and from the roadmap text in #29. Block breaking is `net.neoforged.neoforge.event.level.block.BreakBlockEvent`, not `BlockEvent.BreakEvent`. Config types are `LOCAL`, `CLIENT`, `SYNCED` and `STARTUP` in FancyModLoader 12.0.8. The facade follows the 26.3 names.

## Risks / Trade-offs

- [The side column is a heuristic. An event built in `EventHooks` or `CommonHooks` counts as `both` even when only one side calls the hook.] -> Status does not depend on `both` versus `server`; a phase 4 port checks the call site in the NeoForge source before it maps the event.
- [A `supported` row can still differ in detail: payload fields, cancel semantics, fire order.] -> The phase 4 mapping table has a test per supported row, and the reason column names the known gaps.
- [Pumpkin adds or starts firing events upstream, so statuses go stale.] -> Rerun the generator after each `git merge upstream/master`. Downgrades from unfired events show up on their own.
- [NeoForge 26.3.x moves on: classes, payloads and registries change per release.] -> Rerun against the new commit and diff the tables.
- [Method rows group overloads. A port can need one overload that the facade lacks.] -> The phase 4 mapping table lists overloads where a ported mod uses them.
- [Most rows are `planned` or `not supported`.] -> That is the gap phase 4 and phase 6 close. Pick the order from `modpack-usage.md` (#46), not from this list.
